# Task Four Step 12: security controls deliberately deferred

This records controls considered during the actual product/worker design and this close-out. They are not implemented guarantees or approval to launch without safeguards. The current public authentication flow remains disabled. These deferrals do not change the [PRD](../../docs/PRD.md), add features or claim a prior owner decision that was not supplied.

## Four independent deferred controls

| Control | Present protection and reason for deferral | Remaining risk | Trigger for implementation/review |
| --- | --- | --- | --- |
| Dedicated least-privilege database identity for the mail worker | The reviewed pilot implementation reuses the restricted product runtime; the additive grant changes only outbox attemptCount, availableAt and sentAt. A separate principal adds provisioning/credential-management work before any eligible worker dispatch has run. [Permissions and scope](../../prisma/product/email-worker.md#additive-owner-only-privileges). | A compromised worker has more account-writing privileges than it needs, even though it cannot approve Terms, rewrite identities or create sessions under current grants. | Before unattended deployment or broader worker hosting: review a dedicated worker identity, exact SELECT/UPDATE grants, credential lifecycle and negative privilege tests. Do not broaden the existing role as a substitute. |
| Operational multi-key rotation and managed key lifecycle | HMAC/AES-GCM envelopes carry key IDs and the secret utilities can read a key ring, but the CLI supplies only one active verifier key and one active encryption key. Rotation was explicitly left for review rather than adding an untested operational system. [Worker key limitation](../../prisma/product/email-worker.md#claiming-safety-and-recovery). | Losing/removing an old key makes pending payloads unusable; disclosure threatens pending secrets. Ad hoc replacement can break verification or delivery. | Before real customer jobs: approve protected key storage, dual-read transition/retirement, access/recovery and compromise procedures, with tests for pending jobs across rotation. Current keys must never be guessed or silently replaced. |
| Independent external worker deadline/supervision and stronger fencing | A dedicated session lock, durable attempt reservation, fatal disconnect handling and whole-process 30-second watchdog bound the initial worker. No scheduler/supervisor or external fencing system is installed, avoiding a second queue and unsupported exactly-once claims. [Watchdog limits](../../prisma/product/email-worker.md#claiming-safety-and-recovery). | JavaScript timers can be delayed by process/OS suspension. SMTP acceptance can be uncertain after termination; an external side effect cannot be rolled back by PostgreSQL. A naive restart can duplicate delivery. | Before unattended worker operation or multiple hosts: define supervision, independent termination bounds, stale-owner behavior and uncertain-outcome recovery; test crash/suspension scenarios with explicit owner authorization. This does not promise exactly-once SMTP. |
| Append-only per-dispatch security/operational audit history | Existing jobs retain a bounded counter, status and timestamps; output uses fixed safe outcomes. The eight-table slice deliberately does not add another per-attempt history table before its operational need and data-retention policy are reviewed. [Existing worker audit limits](../../prisma/product/email-worker.md#claiming-safety-and-recovery). | Overwritten current state cannot reconstruct every rejection, uncertain handoff or cancellation. Investigation and detection of repeated abuse are weaker. | Before operational support needs historical incident reconstruction, or when retry/uncertain outcomes occur: approve minimal per-attempt events, access/retention/integrity and safe correlation. Never log codes, payloads, recipients, keys or provider replies merely to obtain more detail. |

These four controls are distinct: principal separation, key lifecycle, execution/fencing and audit integrity. Their rationale is proportionate to a disabled, low-volume implementation with synthetic tests, not evidence that all are safe to omit forever. Triggering a condition requires a new approved implementation slice; this document does not install a service or grant permissions.

## Required launch controls are not optional deferrals

Functional authenticated Login/Reset, verification-gated sessions, trusted ingress and shared account/IP rate controls, complete invitation/business authorization, operational Terms acceptance and legal readiness remain product work. Do not count these missing essentials as permanently omitted optional protections. The in-memory assessment limiter and controlled email benchmark do not supply them.

No runtime AI, retrieval or payment processing is introduced to fill an assessment checklist. Their absence is product scope, not a security-control deferral. Exact-password preservation is an approved policy with a disclosed assessment conflict, not permission to trim credentials later. See [defects and remaining limitations](defects.md).

Assumptions: none. Operational risk acceptance and activation still require owner review.
