## Implemented scope and settings

I added database-free asynchronous hashPassword(password) and verifyPassword({ password, hash }) utilities in [password.server.ts](../../lib/auth/password.server.ts). The owner installed @node-rs/argon2 2.2.2; the existing package-file changes are preserved. WSL Node 24.22.1/Linux x64 and the native hash/verify/parseOptions exports were inspected locally. No dependency installation or network request was made in this implementation slice.

| Setting | Initial value |
| --- | --- |
| Algorithm | Argon2id, explicitly selected. |
| Version | Argon2 v1.3, PHC v=19. |
| Memory cost | 65,536 KiB = 64 MiB total per active computation, plus runtime overhead. |
| Time cost | 3 passes. |
| Parallelism | 1 lane. |
| Output | 32 bytes. |
| Salt | Fresh 16-byte cryptographically random salt per hash, generated by node:crypto. |

This is an initial policy, not calibrated tuning for production. The owner has now captured the local sequential measurements below; deployment calibration remains pending. Memory and repeated passes increase guessing costs; one lane keeps initial concurrency/resource planning simple. Salt is public and encoded with algorithm/version/parameters/output in the PHC string. It prevents identical passwords producing identical stored hashes and frustrates precomputed reuse; it does not replace a slow hash or make weak passwords safe.

Parameter selection draws on [Better Auth's custom hashing example](https://better-auth.com/docs/authentication/email-password) and [OWASP's Argon2id guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), consulted during the preceding readiness work. The selected settings exceed OWASP's stated minimum memory/pass combination; they are not copied benchmark results or a claim of compliance. No new source retrieval occurred in this offline slice.

Before real authentication, measure hash/verify latency, concurrent memory usage, native worker-pool contention and expected load on the actual deployment hardware. Approve rate/concurrency limits and request-byte bounds before exposing endpoints. Parameter upgrades require a reviewed accepted-profile/rehash strategy so existing credentials are not locked out.

## Password preservation and failure behaviour

The utility does not trim, lowercase, normalize, truncate, prehash or log passwords. Ordinary leading/trailing/internal spaces and different Unicode sequences remain significant. Isolated UTF-16 surrogates cannot be preserved through UTF-8 and are rejected rather than silently replaced; align future boundary validation with this representability check before real authentication. This does not change the existing UI policy in this slice.

Signup still uses the [shared schema](../../lib/auth/schemas.ts): minimum 12 Unicode code points, no arbitrary maximum, meaningful spaces allowed, controls and whitespace-only new passwords rejected. The hashing primitive does not enforce enrollment rules; a future boundary must validate first and consume parsed data. Login must not retroactively impose new enrollment lengths.

Malformed/unsupported hashes return false without native error details or logs. The verifier bounds encoded-hash length and checks the exact current Argon2id profile before expensive verification. These are hash-format/resource restrictions, not a new password-length maximum. Other profiles are deliberately unsupported until a reviewed compatibility/rehash policy exists. Hash generation failures raise only a constant PasswordHashingError; verification errors fail closed. Future operational monitoring must distinguish outages safely without recording credentials.

The application uses the standard server-only marker. Next.js enforces its client-import boundary. The [Node CLI/test loader](../../scripts/register-server-only.mjs) maps that marker to Next's bundled server-context module only for standalone Node tools; it is not imported by application code and adds no package.

### Evidence 07 — same password, independent salts

The captured output contains two different Argon2id PHC strings and reports different_hashes=true, first_verifies=true and second_verifies=true. Both were generated from the same fixed synthetic password. Their encoded profiles show v=19, m=65536, t=3 and p=1, consistent with 64 MiB memory, three iterations, parallelism one, 16-byte random salts and 32-byte output. The package's numeric version option 1 represents encoded version 19; it is not a PHC version-1 hash.

A fresh random salt makes repeated hashing of the same password produce different results in this experiment. Salt is public and stored with the hash so verification can reproduce the calculation. Unique salts prevent one precomputed result being reused across many accounts and conceal identical-password equality; they do not make weak passwords strong or replace an expensive password-hashing function.

### Evidence 08 — actual local sequential measurements

| Algorithm | Operations | Total elapsed ms | Mean ms/operation | Estimated operations/second |
| --- | --- | --- | --- | --- |
| Argon2id | 5 | 629.078850 | 125.815770 | 7.948 |
| SHA-256, comparison only | 100,000 | 204.225886 | 0.00204225886 (approximately 0.002042) | 489653.892 |

For elapsed milliseconds T and operation count N:

- Mean milliseconds per operation = T / N.
- Estimated sequential operations per second = N × 1000 / T, equivalently 1000 / the unrounded mean.

Applied to the genuine results:

- Argon2id mean = 629.078850 / 5 = 125.815770 ms; estimated rate = 5 × 1000 / 629.078850 = approximately 7.948 operations/second.
- SHA-256 mean = 204.225886 / 100000 = 0.00204225886 ms; estimated rate = 100000 × 1000 / 204.225886 = approximately 489653.892 operations/second.

Use the measured total rather than the displayed rounded SHA-256 mean for the rate calculation; rounding the mean first produces a different approximation.

Slow, memory-hard password hashing deliberately makes each offline guess more expensive. Argon2id's memory and repeated passes impose costs that a fast general-purpose digest does not. SHA-256 is designed for speed: the captured comparison illustrates why an attacker could evaluate many simple digest guesses quickly. Adding a salt alone would not turn SHA-256 into an adaptive, memory-hard password hash. It is used here only for comparison, never credential storage.

These are **local sequential application benchmarks, not attacker GPU throughput or production-load measurements**. One Argon2id warmup and 1,000 SHA-256 warmups are excluded; measured batches contain five asynchronous Argon2id operations and 100,000 SHA-256 digests. Argon2id includes fresh salt generation, PHC encoding and asynchronous scheduling; SHA-256 includes digest construction. This is not a raw-KDF-only equality comparison, a measured password-cracking attack or authenticated-request throughput.

The files record one local timing batch, not a distribution of results under deployment concurrency. Concurrent load, power/thermal conditions and a Git revision are not recorded in their output and must not be inferred. Deployment hash/verify latency, memory usage and worker-pool contention still require separate calibration. No repetition is needed merely to finalize these captured evidence entries.
