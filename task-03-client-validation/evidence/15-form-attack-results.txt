Browser input handling matters:
- In the three edge-space email trials, the browser's final email value differed from the requested padded sample; all three reached unavailable feedback.
- The Signup newline and verification newline trials also did not preserve the requested raw input; their DOM values reached unavailable feedback.
- These trials are NOT evidence that the validator accepted raw newline characters. The pure-function tests rejected the raw newline samples.
- The browser result records DOM lengths and preservation flags; it does not attribute an unmeasured transformation to application code.
- The fixed bypass pair (a@b plus a one-space password) was blocked by actual Signup errors.

Findings, not invented security incidents
-----------------------------------------
a@b is blocked; a@b.c passes the current coarse email-shape rule. That is not proof of deliverability or ownership.
A 300-character email local part and a Unicode email sample pass that same coarse rule in the validator tests; backend/email-provider policy is not implemented.
Signup whitespace-only passwords are blocked; meaningful leading/trailing spaces are allowed and preserved by the validator.
Login has a presence-only password rule, so a one-character or one-space value can reach unavailable feedback. No credentials are checked and no login occurs.
Six zeros pass code format, not verification. No real OTP challenge exists.
